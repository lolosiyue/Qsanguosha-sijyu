# UI 路線圖計劃（UI Roadmap）

- 狀態：概念提案（Concept，未進入實作排程）
- 日期：2026-09-09
- 適用範圍：本倉庫**所有現有與計劃中的前端殼（shell）與遊玩模式**，不只 Web WASM client
- 規範層級：本文件只定義 **UI 概念、資訊架構與呈現契約**；不定義代碼結構、不含實作代碼、不取代
  [`cross-platform-modernization-plan.md`](cross-platform-modernization-plan.md) 的交付基線

## 0. 本文件是什麼／不是什麼

**是**：在各版本真正動工之前，先把「畫面上有什麼、誰在哪、玩家怎麼知道現在該做什麼」講清楚的一份共用概念稿。
各版本殼可以長得完全不同，但必須回答同一組問題。

**不是**：

- 不含實作代碼、CSS、QML、控件命名或檔案規劃。
- 不排期、不估工時；階段編號只表示**依賴順序**（前一階沒做，後一階會做白工）。
- 不改變任何協議、規則判定或伺服器行為。UI 永遠是 Room 權威狀態的投影。

**特效層的歸屬（全域規則）**：**Spine、emotion（表情動畫）、QML 特效層只存在於 P2 桌面 Qt GUI**，
那裡是它們唯一的顯示地。其他任何殼（Web、TUI、Android、大屏、精簡）在概念與驗收上都**視為不存在**，
不得以它們為前提，也不得把必要資訊只放進特效裡——特效可以強化，不可以承載。

## 2. 共通 UI 契約

不論用 DOM、QGraphicsView、字元格、觸控還是手掣，這八件事在所有殼上必須**語義相同**，
只是表達方式不同。這是「多殼」不會退化成「多套各自演化的產品」的唯一保險。

### 2.1 座次環（Seat Ring）

牌桌不是玩家清單，是**有方向的環**。任何殼都必須表達三件事：

1. **自己永遠在環的近端**（螢幕下方／終端最後一列／dashboard）。
2. **上家與下家的方位**可讀，且與 `CHOOSE_DIRECTION` 決定的順逆時針一致。
3. **座次號**與環上位置一致（距離計算、「你左邊那位」這類語言才能被理解）。

C++ 原版把這件事實作成 8 個矩形區的 U 形分配表（`RoomScene::updateTable()` 的
`s_regularSeatIndex`）。**這張表就是全專案的座次環規範**，其他殼應複用它的語義，
而不是各自發明排列。1v3、3v3 有專用表（`s_hulaoSeatIndex`、`s_kof3v3SeatIndex`），
任何殼要支援這些模式時同樣沿用。

**人數上限與降級**：該表只覆蓋到 **20 人**；超過即無定義。因此座次環有三種呈現層級，
按可用面積與人數自動降級：

| 層級 | 適用 | 呈現 |
|---|---|---|
| **完整環** | ≤ 20 人且面積足夠 | 八區 U 形，每人一張含 L0 的座位卡 |
| **席位帶** | 面積不足（直版、小窗） | 一維帶狀，**保持環序**，可水平拖動／翻頁（見 3.2） |
| **縮略總覽** | > 20 人（M1） | `PlayerMiniItem` 網格 ＋ 焦點面板（見 §5） |

三個層級都必須保持環序與座次號一致；**降級只能減少每人的資訊量，不能打亂順序**。

### 2.2 互動信封（Interaction Envelope）

29 類互動在任何殼上都應該渲染成同一個五段式信封，不因命令不同而換佈局：

```
┌ 標題 ───────────── 期限 ▸▸▸▸▸▸░░░ ┐
│ 提示（主句，大字）                  │
│ 副提示（來源／目標／參數，小字）      │
├ 候選區：可選什麼（牌／角色／選項）    │
├ 草稿區：已選了什麼（可逐項撤銷）      │
└ 動作區：確認 ▸  取消 ▸  （位置固定）  ┘
```

三條不變式：

- **動作區的位置不隨選擇變動**。玩家在連續互動中會形成肌肉記憶，按鈕位移＝誤操作。
- **候選集永遠由規則層給出**，UI 不猜。規則層不可用時進入降級態（見 2.6），而不是放行。
- **草稿可逆**。已選牌可反選、已投目標可撤回、順序可重排——直到按下確認為止。

### 2.3 三層資訊密度（L0 / L1 / L2）

| 層 | 內容 | 出現方式 |
|---|---|---|
| **L0 常駐** | 體力、手牌數、身分、勢力、存活、**回合／階段**、**翻面**、**連環**、標記、裝備、判定區 | 永遠可見，不需互動 |
| **L1 按需** | 牌面細節、技能全文、距離與攻擊範圍推導、出牌歷史次數 | 懸停／長按／聚焦 |
| **L2 深查** | 完整戰報、武將圖鑑、規則書、設定 | 明確開啟的面板或頁 |

判準：**L0 缺一項，玩家就得靠記憶或猜測玩牌**。目前多個殼（含 P1）把本應 L0 的資訊漏在 L1 或完全沒有，
這是最優先要補的一類缺口，優先於任何美化。

M1 是唯一容許 L0 分層的場合：縮略位只保留 **體力／死亡／手牌數／焦點** 四項，其餘 L0 移入焦點面板與詳細卡。

### 2.4 三種訊息流必須分離

| 流 | 內容 | 特性 |
|---|---|---|
| **戰報（log）** | 遊戲事件的權威敘述 | 可回捲、可篩選、不打斷 |
| **聊天（chat）** | 玩家發言 | 可回捲、可輸入、與戰報**視覺可區分** |
| **瞬時（toast／焦點）** | 「輪到你」「連線中斷」「規則引擎降級」 | 短暫、置頂、不進歷史 |

原版桌面把 log 與 chat 用高度百分比切成上下兩塊（`m_logBoxHeightPercentage` /
`m_chatBoxHeightPercentage`），這是正確的分離；其他殼可以摺疊、可以分頁，但**不能把三者混成一條流**。

### 2.5 尺度與主題 token

各殼共用同一組**語義名稱**（非同一份實作）：

- 尺度：`photo`（座位卡）、`mini`（縮略位）、`card`（牌）、`gap`、`text-*`。
- 主題：`bg` / `panel` / `ink` / `muted` / `accent` / `danger`（不可逆）/ `disabled` / `focus`（結算焦點）。
- **顏色不得是唯一的資訊載體**：任何用顏色表達的狀態（可選、已選、不可用、危險、焦點），必須同時有
  形狀、邊框、圖示或文字。這條在 TUI 上是硬需求（去色後必須可讀），在圖形殼與大屏上是無障礙需求。

### 2.6 降級必須可見

四種降級態，任何殼都要有明確表達，且**絕不靜默放行**：

| 降級 | 表達 |
|---|---|
| 規則引擎不可用／版本不符 | 停用「確認」，保留「取消」，說明原因與復原方式 |
| 未知命令／未支援內容 | 可見的失敗訊息＋取消，不猜測 |
| 資產缺失（圖／字體／翻譯） | 退回文字或佔位，不留空白方塊 |
| 連線中斷／重連中 | 全域狀態條，凍結輸入而非丟棄輸入 |

### 2.7 焦點與結算關係（Focus）

玩家在任何時刻都必須能回答三個問題，人數愈多愈重要：

1. **現在是誰的事件**（結算中的主角色）
2. **事件正影響誰**（來源或目標）
3. **其他人大致處於甚麼狀態**

小局用座次環上的高亮＋倒數即可回答；大局需要專屬面板（§5）。**要點是：焦點追蹤的是「結算關係」，
不是「當前回合玩家」**——回合玩家在一次結算鏈裡可能完全不是主角（例如他人的無懈、判定、連環傷害）。

> **前提待確認（協議層）**：目前 `MOVE_FOCUS` 只帶「正在被詢問的玩家名單＋倒數」，
> **「來源→目標」的結算關係不是協議上的一等公民**。焦點面板初期只能由客戶端從
> 出牌／技能／傷害等呈現事件合成。若合成不足以穩定表達關係鏈，才需要討論補協議欄位——
> 那是協議工作，不在本文件範圍，但 M1 動工前必須先有結論。

### 2.8 輸入等價性

同一個對局必須能只用以下任一組輸入完成，不得有「只有滑鼠做得到」的操作：

| 輸入組 | 殼 | 最小集合 |
|---|---|---|
| 指標 | P1 / P2 | 點擊＋懸停＋滾輪 |
| 觸控 | P1 / P4 | 點擊＝選取、長按＝查看、拖動＝巡覽 |
| 鍵盤 | P2 / P3 | 焦點移動＋確認／取消＋編號 |
| 手掣／遙控器 | P7 | **方向鍵＋確認＋返回**（肩鍵為加速，不得為唯一途徑） |

推論：任何殼都必須有一個**可遍歷的焦點順序**（席位→手牌→技能→動作區），順序與座次環一致。
這條契約使 P7 不必重做互動邏輯，也讓 P2 順手獲得完整鍵盤操作。

## 3. P1：WASM Web client（現行重點）

### 3.1 現況診斷

以下每一條都對應現有代碼的實際行為，不是推測。

| # | 現況 | 後果 |
|---|---|---|
| D1 | 座位是置中 `flex-wrap` 的一串卡片（`.photos`），自己被抽離到底部 dashboard | **座次環完全遺失**：看不出上下家、看不出方位，距離與範圍只能讀數字 |
| D2 | 尺寸靠寫死的 `rem`（`.photo` 8.4rem / 6.8rem）＋**只有兩條** media query（`≤719px 或直版`、`≥900px 且橫版`） | 720–899px、超寬、超高、平板全部落在「沒人設計過」的中間帶；人多時只能擠或捲 |
| D3 | 其他玩家的 Photo **只畫延時錦囊**，不畫裝備、不畫私人牌堆、不畫標記 | 判斷「他有沒有武器／防具」必須靠記戰報 |
| D4 | `chained`、`faceup`、`seat`、`phase`、`current_player`、標記、`focus`、`focus_countdown` 皆已在 state 中，**UI 一項都沒渲染** | 資料層已經領先呈現層一整輪；補這些不需要動協議 |
| D5 | 確認／取消在 dashboard 的互動區內，**隨互動類型與選擇狀態改變位置** | 誤點；快節奏互動（無懈、求桃）尤其明顯 |
| D6 | 手牌是 `overflow-x: auto` 的橫向捲軸 | 手牌一多就要捲動才能看全；原版是重疊壓縮，永遠一眼看完 |
| D7 | 房內**只能讀聊天不能發**（輸入框只在等待室），戰報與聊天同一條流 | 違反 2.4 |
| D8 | 記錄面板橫版固定 `12–18rem`，直版固定 `18vh` | 寬螢幕浪費、窄螢幕不夠；無篩選、無摺疊 |
| D9 | 無倒數、無「輪到誰」的視覺焦點 | 玩家不知道還有多久，也不知道在等誰 |

**結論**：P1 目前的問題不在「不夠漂亮」，而在**牌桌的空間語義與 L0 資訊不完整**。
先修 D1–D4，再談其他。

### 3.2 目標畫面語彙

**橫版（主）**——對齊 C++ 原版的 U 形環：

```
┌──────────────────────────────────────────────┬──────────┐
│  ⑦ 上排席位（人多時自動溢出到此）              │  戰報    │
│ ┌────┐                              ┌────┐  │  ────    │
│ │ ②  │            桌面中央           │ ⓪  │  │  聊天    │
│ ├────┤   處理區 / 仁區 / 判定區       ├────┤  │  ────    │
│ │ ④  │        （牌面在此聚合）        │ ③  │  │ 觀戰名單 │
│ └────┘                              └────┘  │ （可摺）  │
├──────────────────────────────────────────────┴──────────┤
│ 自己：立繪｜體力｜裝備｜牌堆｜技能列                      │
│       手牌（重疊壓縮，永不橫捲）                          │
│ ┌ 互動信封：標題／提示／草稿 ─────── 確認 ▸ 取消 ▸ ┐      │
└──────────────────────────────────────────────────────────┘
```

區號 ⓪–⑦ 即原版八區。差別只在 Web 用彈性盒／格線表達，語義一致。

**直版（次）**——U 形摺成「席位帶」，**接受左右拖動／翻頁**：

```
┌────────────────────────────────┐
│ ◂ 席位帶（可左右拖動／翻頁）  ▸ │  ← 環序不變，只是視窗在環上滑動
│  ② ⑦ ⑦ ⓪        ●○○  ⦿當前焦點 │  ← 頁點指示 + 一鍵跳回焦點
├────────────────────────────────┤
│        桌面中央（可縮）           │
├────────────────────────────────┤
│ 戰報／聊天：摺疊為 2 行，可拉開    │  ← 預設收起
├────────────────────────────────┤
│ 自己：立繪＋體力＋裝備（單行）     │
│ 手牌（重疊壓縮）                  │
│ 互動信封（動作區貼底，拇指可及）    │
└────────────────────────────────┘
```

直版席位帶的**四條規則**（拖動／翻頁被允許，但要有護欄）：

1. **只有席位帶可以滑動**。桌面中央、動作區、互動信封永遠固定；不得整頁橫捲。
2. **環序絕不重排**。滑動是「視窗在環上移動」，不是把玩家重新排序或分組。
3. **焦點自動歸位**。輪到誰、正在結算誰、剛被選中的目標，席位帶自動滑到該位置；
   同時提供「跳回當前焦點」與「跳回自己」兩個一鍵動作。
4. **選取時不准找人**。互動進行中，席位帶進入「只看可選」過濾態（可切回全部），
   並顯示 `可選目標 n / 總數`——與 M1 的規則同構（§5.4）。

拖動與翻頁二選一由裝置決定：觸控用慣性拖動＋分頁吸附，滑鼠用滾輪／點箭頭翻頁，兩者的**位置語義相同**。

### 3.3 尺寸階梯

放棄「兩條斷點」的做法，改用**量測—擬合—下發**的概念（原版 `PhotoLayoutFit` 的同構想法）：

1. **量測**可用的牌桌矩形（扣掉工具列、戰報、dashboard）。
2. 依 **座位數 × 區分佈** 擬合出座位卡的層級（小／中／大）與縮放比。
3. 把結果**下發成尺度變數**，牌、立繪、字級全部由它推導。

斷點只用來切換**佈局骨架**，不再用來調尺寸：

| 級別 | 觸發條件 | 骨架 | 戰報／聊天 | 座位卡 |
|---|---|---|---|---|
| **XS** | 短邊 < 480，直版 | 席位帶（可拖動）＋貼底動作區 | 收起（可拉開） | 小 |
| **S** | 短邊 480–720，直版 | 席位帶＋桌面 | 2 行摘要 | 小 |
| **M** | 720–1024，橫版 | U 形環（側欄可收） | 右側可收欄 | 小／中 |
| **L** | 1024–1600，橫版 | U 形環＋固定右欄 | 上下分割 | 中 |
| **XL** | > 1600 或高 DPI | U 形環＋加寬桌面 | 上下分割＋篩選 | 中／大 |

> 方向優先於寬度：直版即使很寬（平板豎持）也走席位帶骨架，因為垂直空間才是稀缺資源。

### 3.4 分階段

| 階段 | 目標 | 完成即可觀測的效果 |
|---|---|---|
| **W1 座次環** | 以原版八區語義重排席位；自己在近端；補座次號與環序；直版席位帶＋拖動／翻頁與焦點歸位 | 能只看畫面說出誰是上下家；直版不需縮小字也能巡覽全場 |
| **W2 擬合尺度** | 量測—擬合—下發取代寫死 rem；斷點只切骨架 | 2–10 人 × 五級尺寸都不出現非預期捲動或裁切 |

| **W4 互動信封** | 固定動作區；倒數用 `focus_countdown`；不可逆操作二次確認；降級態文案統一；席位帶「只看可選」過濾 | 誤操作下降；等待有預期 |

| **W6 訊息流分離** | 房內聊天輸入；戰報／聊天分區；戰報篩選（我的／傷害／技能） | 符合 2.4 |

### 3.5 驗收準則

- 2、5、8、10 人局 × XS/S/M/L/XL 五級 × 橫直兩向：橫版**牌桌不出現橫向捲動、不裁切座位卡**；
  直版允許席位帶滑動，但**桌面中央與動作區不得移動**。
- 直版任一時刻按「跳回當前焦點」，一步到位。
- L0 清單（2.3）每一項都能在不互動的情況下讀到。
- 同一互動在同尺寸下，確認鍵的座標**不隨選擇變化**。
- 規則引擎故意停用時，四種降級態（2.6）全部有可見表達且不可誤送。

## 4. P2：桌面 Qt GUI

**定位**：功能完整度的基準線，也是**特效層的唯一顯示地**（§0）。其他殼可以少做，但不能與它語義相左。

UI 概念上要做的四件事（與 `roomscene.cpp` 的拆分互為表裡，但本文件只談呈現）：

1. **佈局檔案化**：座次區表、間距、面板比例已經是資料（`_m_roomLayout`），應繼續外移，
   讓「4K 桌面」「筆電 1366」「投影 16:10」「超大局」成為可切換的佈局 profile，而不是硬編碼常數。
2. **向量化與高 DPI**：文字、體力珠、身分圖示、邊框優先向量；點陣只保留立繪與牌面。
   目標是 100%–300% 縮放下不糊、不錯位。
3. **主題切換**：把顏色與密度收斂到 2.5 的 token，先支援「深色／淺色」與「標準／緊湊」兩軸。
   皮膚系統（skins）繼續管美術資產，token 管可讀性——兩者不要互相覆蓋。
4. **特效與資訊分離**：Spine／emotion／QML 特效可以獨佔這個殼，但必須可關（低配、錄影、超大局）。
   **關掉特效後不得損失任何 L0／L1 資訊**——這是特效層留在 P2 的代價與前提。

## 5. M1：超大局（50 人）模式 — 限 P2

### 5.1 問題陳述

50 人不是「20 人再多一點」，而是三個機制同時失效：

- **座次環失效**：原版八區表只定義到 20 人；50 人在該模型下無定義，硬塞會把座位卡壓到不可讀。
- **注意力失效**：玩家無法同時追蹤 49 個對手，也不需要——他只需要知道**現在這件事跟誰有關**。
- **選取失效**：從 50 個目標裡翻頁找人，是超大局最大的操作災難。

因此 M1 不是把現有牌桌縮小，而是**換一組呈現元件**，並保留 dashboard 與互動信封完全不變。

### 5.2 佈局概念

```
┌─ PlayerOverviewBar：50 × PlayerMiniItem（滾輪／拖曳巡覽，永不強制翻頁）────────┐
│ ▪▪▪▪▪ ▪▪▪▪▪ ▪▪◆▪▪ ▪▪▪▪▪ ▪▪▪▪▪ ▪▪▪▪▪ ▪▪▪▪▪ ▪▪▪▪▪ ▪▪▪▪▪ ▪▪▪▪▪   可選 7 / 50 │
├───────────────────────────────┬──────────────────────────────────────────────┤
│ Current Resolution Panel      │        桌面中央（處理區／判定／仁區）          │
│ ┌ 主焦點：結算中的角色 ┐       │                                              │
│ │ 大圖 ＋ 完整 L0      │       ├──────────────────────────────────────────────┤
│ └──────────────────────┘      │  戰報（可切「只看焦點相關 / 全部」）           │
│      ↓ 影響                    │                                              │
│ ┌ 次焦點：來源或目標 ┐         │                                              │
│ └────────────────────┘        │                                              │
├───────────────────────────────┴──────────────────────────────────────────────┤
│ 自己：dashboard（與一般局完全相同——這是玩家唯一不需要重新學習的區域）          │
└──────────────────────────────────────────────────────────────────────────────┘
```

### 5.3 三個元件

**PlayerMiniItem（縮略位）**——只做一件事：用角色小圖代表一個人。

- 顯示：角色小圖 ＋ 體力（極簡條或數字）＋ 死亡（灰化／叉）＋ 手牌數 ＋ 回合／結算焦點標記。
- **不顯示**：裝備、判定區、技能、標記明細、身分細節——那些屬於詳細卡。
- 只訂閱四類更新：**血量、死亡、手牌數、焦點**。其餘事件不觸發它重繪。
- 點擊 → 打開該玩家的詳細卡（L1 浮層，含完整 L0＋裝備＋判定＋標記）。

**PlayerOverviewBar（全局縮略列）**——50 個縮略位的容器。

- 排列**嚴格按座次環序**（自己作為環的起點或明顯錨點），永不按分數、存活或勢力重排。
- 巡覽：滑鼠滾輪／拖曳／方向鍵，**不強制翻頁**；翻頁只作為滾動的視覺輔助（頁點指示）。
- 快捷鍵（Tab／Shift+Tab）在**與當前事件相關的角色**之間跳，而不是逐一走過 50 人。
- 恆有兩個一鍵動作：**跳回當前焦點**、**跳回自己**。

**Current Resolution Panel（結算焦點面板）**——M1 的核心。

- 命名建議：正式名 **Current Resolution Panel**，口語可叫 Action Focus；不要用「後視鏡」，
  那個比喻會讓人以為它是歷史回顧，而它其實是**當下**。
- 兩個位：**主焦點 = 正在結算的角色**；**次焦點 = 來源或目標**（視事件方向決定誰在哪一位）。
- 追蹤的是**結算關係**，不是回合擁有者（§2.7）。回合玩家在結算鏈中經常不是主角。
- 關係本身要可讀：兩位之間用一句話說清楚在發生什麼（「A 對 B 使用殺」「B 正在被要求打出閃」）。
- 面板可釘住（跟隨結算自動切換）或鎖定（觀察某人時不被搶走），鎖定態必須明顯標示。

### 5.4 目標選取

超大局最容易毀掉體驗的環節。規則是**永不要求玩家翻頁尋人**：

1. 不可選角色**變暗**；可選角色在縮略列**發光**（顏色以外還要有邊框或角標，見 2.5）。
2. 提供**排序／過濾**：依距離、座位鄰近度、技能合法性；預設「只看可選」，可切回全部。
3. **滾輪循環切換合法目標**，焦點視圖同步顯示當前 hover 的角色（不需點擊即可預覽）。
4. 恆顯示 **`可選目標 7 / 50`**；點數為 0 時直接說明原因（超出距離／被限制／無合法目標）。
5. 已選目標在縮略列與草稿區**雙向可見**，且可從任一處撤回。

這五條同時是 §3.2 直版席位帶的規則來源——**小螢幕與超大局面對的是同一個問題：可視座位少於總人數**。

### 5.5 邊界與驗收

- **範圍**：M1 只在 P2 落地。Web／TUI／Android 不做超大局；若將來要做，必須沿用本節的元件語義，
  不得另起一套。
- **前提**：§2.7 的協議前提必須先有結論，否則焦點面板只能做到「盡力合成」，體驗不穩。
- **效能（概念層）**：50 個縮略位是高頻更新區，只訂閱四類事件、逐項更新，不整列重繪；
  超大局預設關閉特效層（§4 第 4 點）。
- **驗收**：
  - 任何時刻不巡覽、不翻頁，就能回答 §2.7 的三個問題。
  - 一次目標選取全程 **0 次翻頁**完成。
  - 縮略列排序永遠等於座次環序（可用任意時刻截圖核對）。
  - 關閉特效後資訊零損失。

## 6. P3：TUI

board 模式的 UI 概念與 P1 是**同構的**，只是渲染到字元格：

- 座次環：同一張八區表，區內用固定 20×3 的玩家格排布。
- 互動信封：同一個五段式，用邊框字元分段；動作區固定在畫面最後兩列。
- L0：體力用字元條、翻面／連環用字尾標記、標記用角落數字——**去色後仍可讀**（2.5）。
- 三流分離：戰報在右欄，聊天用獨立前綴，瞬時訊息用狀態列。

TUI 的價值不只是「沒有圖形環境時能玩」，而是**它是 UI 契約最嚴格的檢驗器**：
任何無法在字元格上表達的資訊層級，通常代表該資訊在圖形殼上也只是裝飾。
它同時是 §2.8 輸入等價性的天然證明——TUI 能做到的，手掣一定也能。

## 7. P4：Android 客戶端

**不是把 Web 殼包起來**。觸控殼的設計點：

1. **橫版優先**：橫版是第一佈局，直接沿用 U 形環；直版是次要佈局，走 §3.2 的席位帶＋拖動／翻頁，
   並在直版啟用單手模式（動作區貼底、落在拇指弧內）。
2. **兩段式選取**：觸控沒有懸停，L1 資訊改為**長按預覽**；「點一下＝選取，長按＝查看」全域一致，
   絕不讓同一手勢在不同互動裡有不同意義。
3. **中斷友好**：手機會被電話、鎖屏、切換打斷，重連態與倒數必須在回前台時立刻恢復可讀，
   而不是留下一個過期畫面。

**前人探索（`TODO/human`，可參考但不照搬）**：該分支為 Android 做過一套**可拖動懸浮球＋功能面板**，
面板兩列鏡射 PC 選單動作（武將／卡牌一覽、查看棄牌、查看距離、手牌上限、投降等），
底部再鏡射一排放大的技能按鈕（高度 64px），另外把 `ServerDialog` 改成依螢幕尺寸自適應。

評價：**懸浮球解決了「桌面選單在觸控上無處可放」的真實問題，值得保留為 L2 入口**；
但它把 L1／L2 混進同一個抽屜（查看距離、手牌上限這類屬於 L1，不該埋兩層）。建議的界線是——
懸浮球只承載 **L2**（一覽、設定、投降、除錯工具）；**L0 永遠在牌桌上，L1 永遠是長按**。
技能按鈕屬於 L0 操作面，應該留在 dashboard 放大，而不是靠鏡射進浮層。

## 8. P7：大屏／手掣模式

目標場景：電視、Steam Big Picture 式大屏、Android TV、投影；輸入是手掣或電視遙控器，**沒有指標**。

1. **十呎介面**：以 2–3 公尺觀看距離設計。字級、體力珠、牌面辨識度全部按距離放大，
   資訊密度**主動降低**——寧可分兩屏，不要縮到看不清。
2. **焦點導航**：完全依賴 §2.8 的焦點順序（席位→手牌→技能→動作區）。當前焦點必須有
   高對比外框＋位移動效，任何時刻「焦點在哪」不能有歧義。
3. **最小輸入集**：方向鍵＋確認＋返回就能打完整局；肩鍵／快捷鍵只作加速（例如在合法目標間跳），
   不得成為唯一途徑（電視遙控器沒有肩鍵）。
4. **與 M1 同構**：手掣在合法目標間循環的語義，等同 M1 的滾輪切換與直版席位帶的翻頁——
   三者共用同一個「候選集巡覽」概念，只是輸入不同。
5. **多人同屏**：大屏常是多人共用一台。至少要有「隱藏手牌」的快速切換（傳手掣時用），
   否則同屏＝公開手牌。

這個殼的實作成本主要落在焦點導航；如果 §2.8 在 P2 就做對，P7 更接近「換一套尺度 token」而不是重寫。

## 9. P8：精簡模式（探索）

低機率、非承諾。目標裝置：樹莓派、古舊遊戲主機、極低解析度或單色螢幕。

概念上它**不是第七個殼，而是 TUI 契約的再收縮**：

- 座次環 → 編號列表（每人一行：編號、名、體力、手牌數、狀態字元）。
- 互動信封 → 單行提示＋編號輸入（與 TUI classic 同構）。
- 戰報 → 只留最近 N 行；聊天可完全關閉。
- 完全無特效、無立繪、無圖片；字型與顏色皆為可選。

**誠實的技術界線**：ESP32／Arduino 這一級的裝置不具備完整客戶端所需的記憶體、字型與網路棧，
把它們當「完整客戶端」是不現實的。它們**最多只能做顯示端或遙控端**——
例如顯示當前回合、體力總覽、輪到你了的提示，或當作一個「確認／取消」的實體按鈕。
若真要做，應以「第二螢幕配件」而非「客戶端」立項。

## 11. M2：觀戰與重播（最後才做）

**排在所有工作的最後**。它不是一個殼，是任何殼都能進入的模式；UI 概念上與對局殼的差異只有三處：

- **互動信封整段消失**，換成傳輸控制（播放／暫停／速度／跳幀／跳到下一次死亡）。
- **視角切換**：可以把「近端」換成任一玩家；換視角時座次環必須整體旋轉，而不是重排列表。
  在 M1 超大局中，換視角同時要重置縮略列的錨點與焦點面板。
- **資訊權限標示**：明牌／暗牌在重播中可能全可見，UI 必須明確標示「此為上帝視角」，
  避免與對局視角混淆。

之所以放最後：它幾乎完全複用對局殼的呈現層。對局殼未定型前先做觀戰，等於把同一批元件做兩次。

## 13. 依賴順序與風險

**順序**（不是排期）：

1. 共通契約（§2）成文，含 2.7 的協議前提結論、2.8 的焦點順序定義
2. **P1 的 W1／W2 骨架**（含直版席位帶拖動／翻頁）
3. P1 W3–W6 與 **P2 佈局 profile／特效可關** 可並行
4. **M1 超大局**（依賴 2.7 結論與 P2 profile）
5. P4 Android 觸控殼（以 §2＋§7 為輸入）
6. P7 大屏手掣（若 §2.8 做對，成本主要在尺度 token）
7. P8 精簡模式（探索，可隨時中止）
